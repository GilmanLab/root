## Recommendation

- Build `macos/sequoia/desktop` with **Lume’s own CLI and OCI format**, not Packer: Lume 0.5.3 (2026-08-11) supports pinned IPSWs, offline `sequoia` setup, SSH provisioning, cloning, and chunked OCI push/pull under MIT terms ([release](https://github.com/trycua/cua/releases/tag/lume-v0.5.3), [CLI](https://cua.ai/docs/reference/lume/cli-reference), [license](https://github.com/trycua/cua/blob/main/LICENSE.md)).
- Run the image-producing job on a **dedicated, bare-metal Apple Silicon Mac registered directly as a self-hosted runner**. Do not put it inside `incus-gh-runner`: that service creates QEMU VMs on a dedicated Linux Incus host (`incus-gh-runner/README.md:3-6,26-27`), while Lume requires Apple Silicon/macOS and GitHub says nested virtualization is unavailable on its arm64 Mac runners ([GitHub runner limits](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#limitations-for-arm64-macos-runners)).
- Pin the Sequoia IPSW URL and SHA-256, expected `sw_vers` version/build, Lume release asset and SHA-256, and Cua Driver release asset and SHA-256 in git. The current observed Driver tag is 0.28.0, published 2026-09-11 and marked prerelease; its arm64 asset digest is published by GitHub ([release](https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.28.0)).
- Treat macOS TCC as a **human-approved seed step**, not a fully unattended recipe: the supported MDM-less path is `cua-driver permissions grant` in the logged-in GUI, followed by live Accessibility and capture tests; Cua explicitly says not to hand-edit `TCC.db` for reusable seeds ([permissions reference](https://cua.ai/docs/reference/cua-driver/macos-permissions), [seed guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L180-L245)).
- Keep that consented seed host-local by default. Cua’s maintainer guidance says private consented builders/seeds should never be pushed to a registry ([guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L13-L45)); publishing the full macOS disk to private GHCR should be conditional on legal approval.
- If legal review approves registry storage, publish a **private native Lume OCI image** to GHCR with `lume push`; do not wrap it in imgoci because Lume does not consume imgoci indexes and imgoci deliberately does not define conversion or adapters (`~/code/imgoci/spec/README.md:8-31,115-121`).
- GitHub-hosted runners can validate YAML/pins, check manifests, and run host-native Driver tests, but **cannot create, boot, qualify, or practically upload this Lume VM**: standard arm64 Mac runners are M1/3 CPU/7 GB RAM/14 GB disk and nested virtualization is unsupported ([specs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#standard-github-hosted-runners-for-public-repositories)).
- Record both an immutable build tag and manifest digest in the catalog. Lume 0.5.3 only accepts `name:tag`, so resolve and compare the GHCR digest before `lume pull`; literal Lume pull-by-digest needs an upstream feature ([CLI](https://cua.ai/docs/reference/lume/cli-reference#lume-pull), [parser](https://github.com/trycua/cua/blob/main/libs/lume/src/ContainerRegistry/ImageContainerRegistry.swift#L939-L968)).

## Concrete pipeline sketch

### Repository layout

```text
images/
  macos/sequoia/desktop/
    image.yaml                 # CPU/RAM/disk/display, expected OS version/build
    unattended.yaml            # Lume sequoia compatibility/setup config
    provision.sh               # idempotent guest configuration; no secrets
    verify.sh                  # sw_vers, daemon/session, TCC, input/capture smoke
    screen-sharing.mobileconfig-or-settings.md
pins/
  lume.yaml                    # 0.5.3 release URL + sha256: af5d0556…31e6f
  cua-driver.yaml              # 0.28.0 asset URL + sha256: 82ea1801…0d4d6
  sequoia-ipsw.yaml            # Apple URL, sha256, ProductVersion, ProductBuildVersion
catalog/
  macos.yaml                   # build tag, expected OCI digest, local seed name/status
.github/workflows/
  validate-images.yml
  build-macos-sequoia.yml
```

Lume’s release publishes exact checksums, including `lume-0.5.3-darwin-arm64.tar.gz` at `sha256:af5d0556763a7f0116153c220aaabe44974e775091ac57e38da2abb2959c63e8` ([release](https://github.com/trycua/cua/releases/tag/lume-v0.5.3)). Driver 0.28.0 publishes `cua-driver-rs-0.28.0-darwin-arm64.tar.gz` at `sha256:82ea1801a5a800b2e46199e8b88694e8bba5670fd533c63a32766c753300d4d6` ([release](https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.28.0)). Pin release artifacts directly rather than piping moving installer URLs; the Driver installer does support the `CUA_DRIVER_RS_VERSION` override, but the outer installer URL itself moves ([installer source](https://github.com/trycua/cua/blob/main/libs/cua-driver/scripts/install.sh#L1-L35)).

### Workflow

1. **Hosted validation job:** on Ubuntu or hosted macOS, validate schemas, verify that URLs have SHA-256 pins, lint recipe files, ensure tags/actions are immutable, and inspect existing GHCR manifests. Cua can run Driver tests directly on a GitHub-hosted macOS GUI runner, as its own workflow does, but that workflow runs on the host and never launches Lume ([workflow](https://github.com/trycua/cua/blob/main/.github/workflows/e2e-rust-macos.yml)).
2. **Protected build job:** `workflow_dispatch` or a protected release branch, `runs-on: [self-hosted, macos, arm64, lume-builder]`, environment approval, `packages: write`, and a concurrency group of one. Never expose this persistent runner to untrusted pull requests. `incus-gh-runner` is not usable for this job because its worker substrate is a Linux-hosted Incus/QEMU VM (`incus-gh-runner/README.md:25-30`).
3. **Preflight:** require Apple Silicon, host macOS no older than the guest, sufficient free RAM/disk, no running Lume build guest, and the pinned Lume binary/checksum. Lume supports at most two macOS guests; serialize the image workflow and reserve the second slot only for a post-build clone test ([limits](https://cua.ai/docs/reference/lume/limits#macos-vm-concurrency)).
4. **Build:** download and verify the exact IPSW, then run `lume create … --ipsw <file> --cpu 4 --memory 8GB --disk-size 150GB --unattended sequoia`. Lume installs the IPSW, boots once, patches the Data volume offline, enables SSH/autologin/no-sleep, boots again, and verifies SSH ([setup sequence](https://cua.ai/docs/concepts/how-lume-unattended-setup-works)). Do not use `--ipsw latest` in a release build.
5. **Qualify first GUI boot:** attach to the display and verify Setup Assistant is gone before provisioning. Current documentation still says Sequoia may show an Accessibility Setup Assistant step even though issue #2155 was closed ([current concept page](https://cua.ai/docs/concepts/how-lume-unattended-setup-works), [issue](https://github.com/trycua/cua/issues/2155)).
6. **Provision through `lume ssh`:** install the checksummed Cua Driver app/CLI, configure its app-owned daemon to start in the logged-in Aqua session, enable the intended Screen Sharing/VNC fallback, remove transient installers, and verify the exact versions. Cua requires the daemon to be started under `CuaDriver.app`; spawning raw `cua-driver serve` from an unrelated helper is unsupported because TCC follows the responsible app identity ([Driver README](https://github.com/trycua/cua/blob/main/libs/cua-driver/README.md#L160-L172)).
7. **TCC gate:** an operator uses `lume attach`, runs `cua-driver permissions grant`, approves Accessibility and Screen Recording, and triggers a real desktop capture; the CI job can poll the read-only `permissions status --json` until both grants are true. Then fully relaunch the app and repeat `get_accessibility_tree` plus `get_desktop_state` without prompts ([permissions reference](https://cua.ai/docs/reference/cua-driver/macos-permissions), [end-to-end guide](https://cua.ai/docs/how-to-guides/driver/run-in-macos-lume-vm)). Keep the release’s certificate-backed bundle identity stable so the grant is attached to a durable identity; Cua explicitly warns not to approve ad-hoc builds ([seed guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L126-L178)).
8. **Clone smoke:** stop the candidate, clone it, boot the clone headless, verify autologin, SSH, app-owned daemon, Accessibility action, PNG capture, and fallback console/viewer, then stop/delete the clone. A database row alone is insufficient; Cua requires live screenshot and reversible input proof after its disposable-worker seeder ([guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L297-L318)).
9. **Publish, conditional on legal approval:** first run explicit `lume push --dry-run --reassemble`, then `lume push <stopped-vm> macos-sequoia-desktop:<immutable-build-tag> --additional-tags <channel> --organization <org>`. Lume’s default OCI mode chunks the disk; GHCR limits each layer to 10 GB and each upload request to 10 minutes, so keep the 512 MB chunks rather than `--single-layer` ([Lume CLI](https://cua.ai/docs/reference/lume/cli-reference#lume-push), [GHCR limits](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#troubleshooting)). Set `GITHUB_USERNAME`/`GITHUB_TOKEN` only in the host job; Lume reads those for push, and no registry token belongs inside the guest ([source](https://github.com/trycua/cua/blob/main/libs/lume/src/ContainerRegistry/ImageContainerRegistry.swift#L3106-L3114)). GHCR packages first publish private and `GITHUB_TOKEN` can publish from the linked repository ([GHCR docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#pushing-container-images)).
10. **Record provenance:** resolve the pushed OCI manifest digest, reject any attempt to overwrite the immutable tag, attach CI provenance/signature to that digest, and update `catalog/macos.yaml` by reviewed PR. The catalog should carry both `image:tag` and `expected_digest`.

### Last mile into Lume

`agentcompute` resolves `macos/sequoia/desktop` to `{registry, organization, image_tag, expected_digest}`. Before first local use, it performs an OCI manifest `HEAD` for the tag and rejects a digest mismatch; only then does it call `lume pull image:tag seed-name`, stops the seed, and services requests with `lume clone` + `lume run --detach --display none`, matching the design’s Lume mapping (`agentcompute.md:204-216,313-320`). Lume writes the fetched manifest digest into `.manifest-digest`, but 0.5.3’s parser rejects `name@sha256:…` and only accepts `name:tag` ([source](https://github.com/trycua/cua/blob/main/libs/lume/src/ContainerRegistry/ImageContainerRegistry.swift#L919-L968)); therefore true digest-addressed pull remains an upstream gap and there is a tag-resolution TOCTOU risk. Use never-overwritten digest-derived tags until Lume gains digest references.

Do not publish the Mac VM as an imgoci `incus-vm` representation: imgoci is valuable for the Incus image families, but its current public representations describe files such as `incus-vm`, qcow2, raw, and ISO, while Lume expects a paired hardware config/NVRAM/disk manifest with its own media types (`~/code/imgoci/spec/README.md:52-105`; [Lume OCI source](https://github.com/trycua/cua/blob/main/libs/lume/src/ContainerRegistry/ImageContainerRegistry.swift#L214-L237)). Wrapping the Lume image would require a new adapter/representation that neither consumer currently understands.

## Risks and unknowns

- **No supported fully automated MDM-less TCC grant.** Apple’s PPPC payload can pre-allow Accessibility, but for Screen Capture Apple’s example uses `AllowStandardUserToSetSystemService` and still prompts the user ([Apple PPPC example](https://support.apple.com/guide/deployment/privacy-preferences-policy-control-custom-dep9ddb7e0b5/web)). Cua’s checked-in helper can write Accessibility and Screen Capture rows only in a SIP-disabled `VirtualMac` with a verified certificate-backed identity ([helper](https://github.com/trycua/cua/blob/main/libs/cua-driver/tests/runners/macos-lume/seed-tcc-guest.sh)); Cua limits it to disposable workers and says not to use manual database editing for a reusable seed ([guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L205-L212)). Thus the boring production choice is human consent once per seed. Whether those grants survive a **GHCR push/pull** (not merely `lume clone`) is not documented and must be an acceptance test before registry promotion.
- **Public TryCua Sequoia image contents are unverified.** The package page exposes the OCI manifest and tags but no recipe, SBOM, Driver version, or TCC assertion; no macOS image builder was found in Cua’s public `.github/workflows`, and `packer-plugin-lume` contains examples rather than a published image pipeline ([package](https://github.com/orgs/trycua/packages/container/package/macos-sequoia-cua), [workflows](https://api.github.com/repos/trycua/cua/contents/.github/workflows), [plugin](https://github.com/trycua/packer-plugin-lume)). Current Tahoe documentation explicitly says its public base has no TCC grants and installs Driver afterward ([maintainer guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L28-L39)). Do not infer that `macos-sequoia-cua:15.3` satisfies the design.
- **Apple license review is a release gate.** The Sequoia SLA permits at most two additional virtual instances on an Apple-branded Mac for development/testing/server/personal noncommercial use, bars service-bureau/time-sharing uses outside its developer-services terms, prohibits redistribution except as permitted, and permits one backup copy ([Apple SLA §§2B(iii), 2J–K, 3](https://www.apple.com/legal/sla/docs/macOSSequoia.pdf)). A private GHCR package is not an express safe harbor. Keep images host-local unless counsel approves the exact internal registry and agentcompute use; never publish them publicly.
- **Hosted runners cannot build this image.** GitHub’s standard arm64 Mac is an M1 with 7 GB RAM and 14 GB disk, while Lume recommends 16 GB host RAM and ≥50 GB free even for one 8 GB guest; GitHub also explicitly disables nested virtualization ([GitHub specs/limits](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Lume limits](https://cua.ai/docs/reference/lume/limits)). Apple says nested virtualization requires M3 or later in any event ([Virtualization framework](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported)). Hosted jobs are suitable only for validation, metadata, and direct-host Driver tests.
- **Build duration is unquantified.** No official wall-clock timings were found in Lume’s CLI reference, unattended-setup explanation, release changelog, or Cua’s macOS seed guide. Cold duration includes a full IPSW install with two verification boots, guest provisioning, GUI consent, a clone/reboot smoke, gzip/chunk processing, and transfer of a disk currently seen as 80–150 GB logical ([setup sequence](https://cua.ai/docs/concepts/how-lume-unattended-setup-works), [public package](https://github.com/orgs/trycua/packages/container/macos-sequoia-cua/1120319244?tag=15.3), [seed guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L19-L26)). Start with a six-hour job timeout and capture phase timings; that timeout is **[INFERENCE]**, not a published benchmark.
- **Sequoia unattended first boot remains suspect.** Issue #2155 was closed 2026-08-12, but the current Lume concept documentation still says the Sequoia preset can show Setup Assistant’s Accessibility step ([issue](https://github.com/trycua/cua/issues/2155), [current docs](https://cua.ai/docs/concepts/how-lume-unattended-setup-works)). Make first-display boot a blocking qualification, not an assumed property.
- **Digest pinning has a last-mile gap.** GHCR supports standard `@sha256:` pulls ([GHCR docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#pull-by-digest)), but Lume 0.5.3 accepts only `name:tag`. Preflight digest comparison plus append-only tags mitigates but does not eliminate the race; request upstream digest-reference support.
- **Security posture of the consented seed:** it contains durable TCC authorization and possibly a signing identity, so compromise grants desktop control. Cua’s own model keeps such seeds immutable, private, stopped, and host-local, never copies source-control/registry credentials into them, and warns against registry push ([guide](https://github.com/trycua/cua/blob/main/docs/content/docs/how-to-guides/driver/run-tests-in-macos-lume-vm.mdx#L38-L45,L108-L110,L247-L271)). If GHCR publication is approved, scrub all keys/tokens and verify that only the public release-signed Driver identity—not a private signing keychain—is present.
