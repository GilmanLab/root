## Recommendation

- Use **distrobuilder 3.3.1** for both Linux deliverables: a system-container image for `router` and a split QCOW2-plus-metadata VM image for `ubuntu/24.04/desktop`. It is the Incus project's purpose-built system-container/VM builder and emits Incus-importable artifacts directly ([build documentation](https://linuxcontainers.org/distrobuilder/docs/latest/howto/build/), [v3.3.1, 2026-02-24](https://github.com/lxc/distrobuilder/releases/tag/v3.3.1)).
- Build only from protected `main`/release workflows on a dedicated, ephemeral `incus-gh-runner` image allowed to use narrowly scoped `sudo`; distrobuilder refuses non-root execution, while the normal runner contract starts jobs as non-root (`actions-runner`) ([source](https://github.com/lxc/distrobuilder/blob/main/distrobuilder/main.go#L135-L139), `/Users/josh/code/meigma/incus-gh-runner/docs/docs/how-to/build-runner-images.md:49-68`).
- **Nested KVM is not needed to assemble either distrobuilder artifact**: the VM path creates a raw disk through loop devices and converts it with `qemu-img`; it does not boot QEMU ([VM source](https://github.com/lxc/distrobuilder/blob/main/distrobuilder/vm.go#L187-L215), [packing source](https://github.com/lxc/distrobuilder/blob/main/image/incus.go#L90-L100)). Boot-test against a restricted Incus project on the physical cluster, rather than starting a nested VM inside the runner.
- Pin Ubuntu packages with an Ubuntu Snapshot ID, pin distrobuilder/source downloads and Cua Driver by version plus SHA-256, and record finished-file hashes; Ubuntu 24.04 supports archive snapshots natively ([Ubuntu Snapshot Service](https://snapshot.ubuntu.com/), `/Users/josh/code/meigma/incus-gh-runner/docs/docs/how-to/build-runner-images.md:54-64,147-150`).
- Publish the desktop split pair to GHCR with imgoci's `target=incus, representation=incus-vm`; use BigOCI when the disk is too large for a single reliable registry blob (`/Users/josh/code/imgoci/spec/README.md:93-118`).
- Publish `router` as a unified Incus tarball, but first settle one imgoci extension representation such as `incus-container`; imgoci accepts unknown selector values, yet currently standardizes only `incus-vm` for Incus (`/Users/josh/code/imgoci/spec/README.md:118-149`).
- Reconcile GHCR digests into Incus with the existing imgoci Go client followed by `incus image import ... --alias ...`; Incus can import unified or split images but does not understand imgoci indexes itself ([Incus import](https://linuxcontainers.org/incus/docs/main/howto/images_copy/#import-an-image-from-files), `/Users/josh/code/imgoci/spec/README.md:121-149`).
- Do **not** choose Packer/Incus (BUSL plus a community plugin), bootc (Fedora/CentOS-oriented and no supported Ubuntu bootc base found), or cloud-init-at-launch for these immutable catalog images.

### Runner sizing and duration

No upstream project publishes representative elapsed times or peak resource measurements for these exact two images, and no build was run during this research. Therefore, “typical duration” is **not verified**. Standard GitHub-hosted Linux runners provide only 14 GB SSD (2 vCPU/8 GB in private repositories; 4 vCPU/16 GB in public repositories), although they do provide passwordless `sudo`; 14 GB is a poor fit for a desktop rootfs plus raw disk, QCOW2 conversion, caches, and OCI staging ([GitHub runner specification](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#supported-runners-and-hardware-resources)).

Initial **planning reservations, not measured requirements**: `router` builder 4 vCPU, 4–8 GiB RAM, 30 GiB scratch, 15-minute job timeout; Ubuntu desktop builder 8 vCPU, 16 GiB RAM, 100–120 GiB scratch, 90-minute timeout; physical-cluster smoke VM 4 vCPU, 8 GiB RAM, 40–50 GiB root disk. Capture wall time, peak RSS, scratch high-water mark, downloaded bytes, and final encoded/decoded sizes on the first three builds, then right-size. IncusOS's own test target uses 4 CPUs, 8 GiB, and 50 GiB, but that is corroborating context—not a measurement of this desktop image ([IncusOS Makefile](https://github.com/lxc/incus-os/blob/main/Makefile)).

## Concrete Linux pipeline sketch

### Repository layout

```text
images/
  pins.yaml                         # builder/tool versions, source SHAs, snapshot IDs
  router/
    distrobuilder.yaml              # Alpine/Debian release, packages, OpenRC/system config
    files/opt/router/...            # only durable appliance helpers/config
  ubuntu-24.04-desktop/
    distrobuilder.yaml              # Incus VM target, packages, agent/fstab generators
    files/etc/gdm3/custom.conf
    files/etc/systemd/user/cua-driver.service
    files/etc/systemd/user/x0vncserver.service
    files/etc/skel/...              # deterministic automation-user session configuration
.github/workflows/
  images-validate.yml
  images-publish.yml
```

Keep recipes in the `agentcompute` repository as the design already directs (`/Users/josh/code/lab2/.wt/feat-agentcompute-design/docs/docs/designs/drafts/agentcompute.md:363-365`). Put tool/source pins in `images/pins.yaml`: distrobuilder tag and source digest; Ubuntu `APT::Snapshot` timestamp; Alpine release and exact package constraints; Cua Driver version, asset name, and SHA-256; and the immutable builder-runner image fingerprint/digest. Pin every GitHub Action to a full commit SHA.

### Recipe contents

- **`router`:** build a system container, preferably Alpine for small size if the team is comfortable with OpenRC, containing `nftables`, `frr`, `iproute2` (including `tc`), `dnsmasq`, `wireguard-tools`, and `tcpdump`, plus only the durable `/opt/router` helpers named by the design (`/Users/josh/code/lab2/.wt/feat-agentcompute-design/docs/docs/designs/drafts/agentcompute.md:210-213,252-259`). Distrobuilder natively handles `apk`/`apt`, package sets, repositories, and file injection ([package reference](https://linuxcontainers.org/distrobuilder/docs/latest/reference/packages/), [generator reference](https://linuxcontainers.org/distrobuilder/docs/latest/reference/generators/)).
- **`ubuntu/24.04/desktop`:** use Ubuntu 24.04 Noble at a fixed snapshot; include boot/EFI packages, `ubuntu-desktop-minimal`, `ubuntu-session`, accessibility bridges, Incus agent units, and `tigervnc-scraping-server`. Noble's `ubuntu-desktop-minimal` 1.539 pulls GDM, GNOME Shell, `ubuntu-session`, AT-SPI, and the toolkit bridge ([package](https://packages.ubuntu.com/noble/ubuntu-desktop-minimal)); `ubuntu-session` already installs `/usr/share/xsessions/ubuntu-xorg.desktop`—there is no Noble `ubuntu-session-xsession` package ([file list](https://packages.ubuntu.com/noble/all/ubuntu-session/filelist), [negative package result](https://packages.ubuntu.com/noble/ubuntu-session-xsession)).
- Disable Wayland in GDM and select the `ubuntu-xorg` session for a dedicated auto-login automation user. This matches the design's explicit Xorg requirement and Cua's strongest Linux lane: X11/Xorg is supported for discovery, capture, AT-SPI, foreground input, and desktop scope, with toolkit-specific limits ([Cua platform support](https://cua.ai/docs/reference/cua-driver/platform-support), `/Users/josh/code/lab2/.wt/feat-agentcompute-design/docs/docs/designs/drafts/agentcompute.md:147-156,210-216`).
- Fetch a **reviewed, exact** Cua Driver release asset and its checksum instead of running a floating curl-pipe installer. The installer honors `CUA_DRIVER_RS_VERSION`, and releases carry `checksums.txt`; current 0.28.0 (2026-09-11) is marked **prerelease**, so it must not be silently treated as a stable production pin ([installer](https://cua.ai/driver/install.sh), [0.28.0 release](https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.28.0)). Install a systemd **user** service bound to the graphical session; Cua's repository has a developer-only installer that demonstrates a Linux user-unit autostart route, while the public installer does not offer `--autostart` ([developer installer](https://github.com/trycua/cua/blob/main/libs/cua-driver/scripts/install-local.sh)).
- Use TigerVNC's `x0vncserver` so the fallback mirrors the same Xorg display instead of creating a second desktop; `tigervnc-scraping-server` 1.13.1 is available for Noble and TigerVNC documents that `x0vncserver` shares an existing X server ([Ubuntu package](https://packages.ubuntu.com/noble/tigervnc-scraping-server), [x0vncserver](https://tigervnc.org/doc/x0vncserver.html)). Do not bake a reusable VNC password; inject an instance secret or confine the listener to the private management path.

### Workflow steps

1. **Validate on pull requests:** parse both YAML definitions, check every referenced local file and declared digest, and ensure pins are complete. Do not expose GHCR write credentials or Incus cluster credentials to pull-request code.
2. **Build on protected `main`, schedule, or manual dispatch:** select a dedicated ephemeral `incus-gh-runner` publisher image. The job starts unprivileged per the runner contract, then a tightly controlled root step invokes the pinned distrobuilder; never execute an unreviewed PR recipe as root (`/Users/josh/code/meigma/incus-gh-runner/docs/docs/how-to/build-runner-images.md:49-68`).
3. **Assemble artifacts:** run `distrobuilder build-incus ... --type=unified` for `router`, and `distrobuilder build-incus ... --vm --type=split` for the desktop. The latter yields `incus.tar.xz` plus `disk.qcow2` ([distrobuilder output contract](https://linuxcontainers.org/distrobuilder/docs/latest/howto/build/#incus-image)). Keep build cache separate from the final output and record decoded-file SHA-256 values.
4. **Smoke-test on a restricted physical-cluster project:** import under a temporary fingerprint/alias, launch a disposable instance, then remove it. For `router`, verify all required binaries, both init/service configuration and a two-NIC forwarding/`tc netem` exercise. For desktop, wait for `incus-agent`, verify `$XDG_SESSION_TYPE=x11`, the Cua user daemon, one harmless `cua-driver call`, a screenshot, and an authenticated VNC handshake against the same display. This uses physical host KVM, so the runner VM needs no nested KVM; it does require a narrowly scoped Incus client certificate/project.
5. **Publish only after smoke success:** create an imgoci release index in GHCR. Desktop entries use `incus-vm` with `metadata` and `disk` roles (the imgoci implementation's default pair is `disk` plus `metadata`, not `rootfs`: `/Users/josh/code/imgoci/go/internal/index/validate.go:396-399`, `/Users/josh/code/imgoci/go/docs/docs/how-to/resolve-deliverables.md:139-142`). Let imgoci/BigOCI handle OCI manifests and multipart blobs rather than adding an ORAS shell format (`/Users/josh/code/imgoci/spec/README.md:103-116`). Publish immutable version tags and record the release-index digest; make a channel tag only a mutable pointer.
6. **Attest:** preserve the finished-file checksums and attach build provenance to the published digest, matching the runner-image project's own guidance (`/Users/josh/code/meigma/incus-gh-runner/docs/docs/how-to/build-runner-images.md:147-150`).
7. **Last mile to Incus:** a separately authorized reconciler resolves the desired GHCR index **by digest** with `~/code/imgoci/go`, retrieves and verifies all roles, then calls `incus image import`. For the desktop this is `incus image import metadata.tar.xz disk.qcow2 --alias ubuntu/24.04/desktop`; for the router it is the retrieved unified tarball and alias `router`. Move the stable alias only after import and a cluster-side smoke check. This adapter is necessary because imgoci deliberately does not make existing catalog readers understand its index (`/Users/josh/code/imgoci/spec/README.md:121-149`).
8. **Optional later native remote:** if operators need `images:`-style browsing and auto-update, mirror the already-built split files through `incus-simplestreams add` and serve the generated static tree over HTTPS; Incus supports SquashFS and QCOW2 there ([Incus simplestreams tooling](https://linuxcontainers.org/incus/docs/main/reference/image_servers/#tooling-to-manage-a-simplestreams-server)). Do not start with this second catalog unless native remote behavior is needed.

## Risks and unknowns

1. **imgoci container vocabulary is unresolved.** The spec defines and validates `incus-vm`, but no `incus-container` representation was found in the spec, Go implementation, or conformance fixtures. Unknown selector values are legal, so a documented extension is possible; settle its roles and whether the payload is unified or split before publishing `router` (`/Users/josh/code/imgoci/spec/README.md:118-149`).
2. **There is no native Incus/imgoci reader.** Incus natively consumes its own import format, simplestreams, Incus servers, or ordinary OCI **application** images; an imgoci-to-`incus image import` reconciler is required ([Incus image servers](https://linuxcontainers.org/incus/docs/main/reference/image_servers/), `/Users/josh/code/imgoci/spec/README.md:143-149`). Do not point `incus remote add --protocol=oci` at an imgoci OS-release index and expect it to become an Incus VM/system image.
3. **Root boundary.** Distrobuilder is root-only and manipulates loop devices ([source](https://github.com/lxc/distrobuilder/blob/main/distrobuilder/main.go#L135-L139), [VM source](https://github.com/lxc/distrobuilder/blob/main/distrobuilder/vm.go#L187-L215)). This conflicts with the general hardened runner rule that job code must not start root. Isolate the publisher runner group, restrict it to protected refs, and prefer a minimal reviewed root wrapper or dedicated build service over general passwordless sudo.
4. **Cluster credential boundary.** A broad Incus client certificate is effectively infrastructure control; the existing runner controller documentation already calls `incus-admin` root-equivalent (`/Users/josh/code/meigma/incus-gh-runner/README.md:28-30`). Use a dedicated build-test project and the narrowest certificate restrictions Incus 7.4 permits. Whether the required import/launch/delete operations can be restricted tightly enough is **unverified**.
5. **Nested virtualization is deliberately avoided, not proven available.** If smoke tests are moved into the ephemeral runner VM, enable and validate nested virtualization on the IncusOS host and expose `/dev/kvm`; a VM with `security.nesting=false` has VMX/SVM removed ([Incus security option](https://linuxcontainers.org/incus/docs/main/reference/instance_options/#instance-options-security)). Host CPU support and the actual `incus-gh-runner` profile were not inspected.
6. **Desktop session details need one real acceptance run.** Exact GDM auto-login/session selection, systemd user-environment propagation (`DISPLAY`, Xauthority, D-Bus), headless virtual display behavior, screen lock/blanking, and Cua daemon restart semantics are not specified by an upstream Ubuntu+Cua VM recipe. No such canonical recipe was found in the Cua repository, Cua docs, distrobuilder recipes, or Ubuntu package docs. Treat the first physical-cluster smoke as a release gate, not an assumed configuration.
7. **Cua release maturity.** The newest researched driver asset, 0.28.0 dated 2026-09-11, is a GitHub prerelease even though it provides checksums ([release](https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.28.0)). The owner must choose and record an approved version; “latest” is not a reproducible or maturity-safe policy.
8. **Snapshot retention.** Ubuntu guarantees snapshots only back to at least two years, not indefinitely ([snapshot service](https://snapshot.ubuntu.com/)). Preserve the exact downloaded package closure in an internal cache/mirror if rebuildability beyond that window is required.
9. **Bit-for-bit output is not automatic.** Distrobuilder stamps current creation/expiry time ([source](https://github.com/lxc/distrobuilder/blob/main/image/incus.go#L183-L204)); filesystem and compression tooling can also vary. Pinning recipes gives repeatable intent and package closure, but byte-identical artifacts require fixed timestamps and a pinned build environment. Whether current distrobuilder exposes every needed timestamp override is **unverified**.
10. **Resource/time numbers are unknown.** No relevant benchmark was found in distrobuilder, mkosi, bootc-image-builder, Incus, Cua, or the local runner docs, and this research did not execute a build. Use the proposed reservations only to obtain measurements, then replace them with observed p50/p95 figures.
